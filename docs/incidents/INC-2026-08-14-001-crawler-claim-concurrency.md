# INC-2026-08-14-001: ошибка `500` при получении crawler-задания

## Карточка инцидента

| Поле | Значение |
|---|---|
| Дата обнаружения | 14.08.2026 |
| Компоненты | `products-api`, `crawler-worker`, PostgreSQL |
| Затронутый endpoint | `POST /api/products/crawler-jobs/worker/claim` |
| Уровень влияния | Средний: не работала очередь crawler, остальные части Product API оставались доступны |
| Потеря данных | Не обнаружена |
| Повреждение БД | Не обнаружено |
| Статус | Исправлено в коде; исправление применяется при следующем deploy |
| Изменение, после которого проявился сбой | `39223e9 feat(admin): add auto parser with scheduled jobs` |

## Краткое описание

После запуска отдельного контейнера `crawler-worker` процесс успешно подключался к Product API, но не мог получить задание из очереди. Каждый запрос на получение задания завершался ответом `500`:

```text
Maketto crawler worker запущен. Product API: http://products-api:8080/api/products
Ошибка очереди crawler: API 500: {"title":"An unexpected error occurred","status":500,"errors":null}
```

Worker не завершал процесс и продолжал повторять запросы, поэтому сам контейнер оставался в состоянии `Up`. Однако ни ожидающие, ни повторно поставленные задания не могли перейти к выполнению.

## Влияние

- задания можно было создавать и видеть в админке;
- `GET /api/products/crawler-jobs` продолжал отвечать `200`;
- worker не мог забрать следующее задание;
- парсинг страниц Maketto и батч-импорт товаров не начинались;
- каталог, обычный импорт товаров и другие части админки не были затронуты;
- удаления или дублирования товаров из-за этого сбоя не произошло.

## Диагностика

### 1. Проверка секрета worker

Product API отвечал `500`, а не `401`. Это подтвердило, что `CRAWLER_API_KEY` был передан обоим контейнерам и проверка заголовка `X-Crawler-Key` проходила успешно.

### 2. Проверка контейнеров

Контейнеры `products-api`, `products-postgres` и `crawler-worker` находились в состоянии `Up`, а PostgreSQL был `healthy`. Значит, причиной не являлись остановка контейнера или недоступность сети Docker Compose.

### 3. Проверка схемы PostgreSQL

В базе присутствовали обе таблицы очереди:

```text
crawler_jobs
crawler_job_logs
```

В `__EFMigrationsHistory` присутствовали миграции:

```text
20260814012000_AddCrawlerJobs
20260814123500_AddCrawlerJobHistoryDetails
```

Таким образом, версия схемы соответствовала приложению, а ручное создание таблиц или пересоздание volume не требовалось.

### 4. Проверка исключения Product API

Стек Product API показал фактическую ошибку:

```text
Microsoft.EntityFrameworkCore.DbUpdateConcurrencyException:
The database operation was expected to affect 1 row(s), but actually affected 0 row(s)
```

Исключение возникало в `CrawlerJobsController.Claim` при вызове `SaveChangesAsync`. Повторные запросы воспроизводили ошибку в одной и той же точке.

## Первопричина

Первоначальная реализация `Claim` использовала read-modify-write через отслеживаемую EF Core сущность:

1. Product API загружал ожидающее задание как tracked-сущность;
2. менял у неё статус и счётчики в памяти;
3. добавлял запись лога через navigation-коллекцию `job.Logs`;
4. одним `SaveChangesAsync` пытался сохранить весь изменённый граф.

У нового `CrawlerJobLog` заранее был задан `Guid`. При добавлении такого объекта к navigation-коллекции уже существующего задания его состояние для EF могло стать неоднозначным: вместо гарантированного `INSERT` формировалась операция над якобы существующей строкой. Строки с таким идентификатором в БД ещё не было, поэтому операция затрагивала `0` строк, а EF Core выбрасывал `DbUpdateConcurrencyException`.

Дополнительно сам алгоритм получения задания был построен как отдельные чтение и последующее сохранение. Даже без ошибки лога эта схема оставляла окно гонки: два почти одновременных запроса могли прочитать одно и то же задание до изменения его статуса.

## Почему worker не упал полностью

Внешний цикл worker перехватывал ошибку Product API, выдерживал паузу и снова опрашивал очередь. Кроме того, для контейнера задано `restart: unless-stopped`. Поэтому процесс и VPS оставались доступны, но очередь фактически не продвигалась.

## Исправление

Исправление внесено в [CrawlerJobsController.cs](../../src/products/Products.Api/Controllers/CrawlerJobsController.cs).

### 1. Атомарный захват задания

Чтение кандидата выполняется без отслеживания через `AsNoTracking`. Переход `Pending → Running` выполняется условным `ExecuteUpdateAsync` непосредственно в PostgreSQL:

```text
UPDATE crawler_jobs
SET Status = Running, ...
WHERE Id = выбранный_id AND Status = Pending
```

Результат обновления обязательно проверяется:

- изменена одна строка — задание успешно получено worker;
- изменено ноль строк — другой запрос уже изменил задание, текущий запрос безопасно получает `204 No Content`.

Это исключает выдачу одного задания двум worker и не требует optimistic update tracked-сущности.

### 2. Безопасный возврат зависших заданий

Задания с просроченным heartbeat также переводятся обратно в `Pending` через условный `ExecuteUpdateAsync`. Обновление выполняется только если задание всё ещё имеет статус `Running` и heartbeat действительно устарел.

### 3. Явный `INSERT` логов

Новая запись истории теперь явно добавляется через:

```csharp
_db.CrawlerJobLogs.Add(log);
```

За счёт этого состояние записи однозначно равно `Added`, даже если `Guid` был создан приложением заранее. EF Core формирует `INSERT`, а не пытается обновить несуществующую строку.

### 4. Транзакция с проверяемыми переходами состояния

Используется транзакция `ReadCommitted`, а целостность обеспечивается условиями в самих `UPDATE`. Такой подход проще обрабатывает повторные запросы и пригоден для запуска нескольких worker в будущем.

## Почему исправление безопасно для данных

- структура таблиц не изменяется;
- миграции не откатываются;
- volume PostgreSQL не пересоздаётся;
- существующие задания и логи сохраняются;
- товары не удаляются и не изменяются;
- повторный claim меняет только состояние подходящего задания;
- уже импортированные батчи остаются в каталоге.

## Развёртывание исправления

После commit и push в ветку `main` GitHub Actions собирает новый образ Product API и выполняет его пересоздание вместе с crawler-worker.

Если требуется вручную применить уже опубликованные образы на VPS:

```bash
cd ~/order-tracking
docker compose -f docker-compose.prod.yml pull products-api crawler-worker
docker compose -f docker-compose.prod.yml up -d --force-recreate products-api crawler-worker
```

Удалять контейнер PostgreSQL, volume или таблицы не нужно.

## Проверка после deploy

### Состояние контейнеров

```bash
docker compose -f docker-compose.prod.yml ps products-api products-postgres crawler-worker
```

Ожидаемый результат: все три контейнера имеют состояние `Up`, PostgreSQL — `healthy`.

### Логи

```bash
docker compose -f docker-compose.prod.yml logs --since=5m products-api crawler-worker
```

В логах не должно быть новых сообщений:

```text
DbUpdateConcurrencyException
API 500
```

При пустой очереди worker должен продолжать работать без ошибок. При наличии задания ожидается переход `Ожидает → Выполняется`, увеличение номера страницы и появление логов импорта.

### Функциональная проверка

1. Открыть `Товары → Импорт JSON → Задачи crawler`.
2. Создать небольшое задание на 1–2 страницы.
3. Убедиться, что оно переходит в статус `Выполняется`.
4. Проверить изменение прогресса и появление импортированных товаров.
5. При необходимости проверить кнопку отмены на отдельном тестовом задании.

## Безопасные действия при повторении

Если ошибка снова блокирует очередь, worker можно временно остановить без остановки Product API и базы:

```bash
docker compose -f docker-compose.prod.yml stop crawler-worker
```

После этого следует собрать диагностику:

```bash
docker compose -f docker-compose.prod.yml logs --tail=300 products-api
docker compose -f docker-compose.prod.yml logs --tail=100 crawler-worker
```

После установки исправленного образа worker запускается командой:

```bash
docker compose -f docker-compose.prod.yml up -d crawler-worker
```

Не следует выполнять `down -v`, удалять `products_postgres_data`, вручную удалять строки очереди или откатывать миграции без отдельного резервного копирования и анализа.

## Меры предотвращения повторения

1. Все переходы состояния очереди выполнять условными атомарными обновлениями в БД.
2. Для новых сущностей с назначаемыми приложением `Guid` явно использовать `DbSet.Add`.
3. Проверять количество строк, затронутых `ExecuteUpdateAsync`.
4. Добавить интеграционный тест параллельного вызова `worker/claim` с реальным PostgreSQL: одно задание может получить только один запрос.
5. Добавить тест создания лога для уже существующего crawler-задания.
6. Сохранять в логах идентификатор задания и название перехода состояния.
7. Настроить оповещение при серии ответов `500` от worker endpoint.

## Итог

Инцидент был вызван не миграциями, секретом или повреждением PostgreSQL, а способом сохранения tracked-графа EF Core при выдаче задания. Переход на атомарное условное обновление и явное добавление логов устранил непосредственную ошибку и одновременно сделал очередь устойчивой к повторным и конкурентным запросам.
